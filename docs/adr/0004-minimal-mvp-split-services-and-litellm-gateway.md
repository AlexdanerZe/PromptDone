# 0004: 极简 MVP 前后端独立迭代与 LiteLLM 网关部署

- **Status**: accepted
- **适用范围**: [极简 MVP 技术决策](https://github.com/AlexdanerZe/PromptDone/issues/65)。本决策只约束新的极简 MVP；不改写其他轨道的 ADR-0001、ADR-0002、ADR-0003。
- **关联地图**: [PromptDone 极简 MVP 需求文档与关键决策](https://github.com/AlexdanerZe/PromptDone/issues/60)。

## 背景与已确认约束

用户要求先交付极简 MVP，并能够快速调整和验证页面、数据处理逻辑与 Prompt。用户明确指定通过 LiteLLM API 调用模型，且 LiteLLM 由本项目一并部署；本轮进一步提出前后端逻辑应独立以支持快速迭代。

已收口的产品约束包括：单文件不超过 20 MB、单次导入少于 50,000 条记录；数据与运行配置可追溯；线性单轮节点；结果逐条保存；页面刷新不取消任务；服务中断后保留结果并手动重跑，首版不承诺自动续跑。

用户已审阅并确认四服务方案、前后端独立迭代与本文件中的运行边界。以下记录已接受的技术约定，不代表工程骨架已实现或服务已部署。

## 决策：同仓库、前后端独立开发和交付

React + TypeScript（Vite）负责页面与交互；Python FastAPI 负责业务规则、数据处理、运行状态与模型调用。两者通过 HTTP API 协作，按功能修改各自代码，不直接互相依赖运行时内部对象。

实现时采用以下目录职责；本 ADR 不创建工程骨架：

```text
apps/web/          前端页面、交互与生成的 API 客户端
apps/api/          后端接口、数据处理、评估与批量执行
infra/litellm/     网关模型别名配置，不存真实凭证
infra/            Compose、开发与交付配置
docs/             需求、决策与验收说明
```

后端以 Pydantic/OpenAPI 定义接口，生成前端 TypeScript 类型与客户端，构建时检查契约是否同步。首版不拆成多个业务微服务。

### 开发环境

- 前端独立运行 Vite，使用 HMR；通过 `/api` 代理调用独立的 FastAPI 开发服务。
- 后端独立运行开发重载进程；前端界面调整不要求重启后端、LiteLLM 或数据库。
- LiteLLM 与 PostgreSQL 可由 Compose 常驻，前后端开发进程分别启动，也可使用各自的开发容器。
- 可用固定小数据和可编程模型响应替身独立验证界面及数据逻辑；真实网关联调用于验证模型参数、响应形状、usage 和费用信息。
- 后端代码重载会重启 API 进程。进程内任务不能承诺跨重载继续执行；需要保留已完成结果、识别中断并允许手动重跑。若未来要求更新后端时跑批仍持续执行，再引入独立 Worker。

### 交付环境：四个服务

- **web**：托管前端构建产物，可使用 Nginx 提供静态文件并将 `/api` 反向代理至后端，使页面与业务 API 同源。前端可独立构建、更新。
- **api**：单进程 FastAPI，关闭开发重载，处理业务接口、限并发模型调用和后台任务；状态及已完成结果写入 PostgreSQL，页面轮询持久态。
- **litellm**：独立 LiteLLM HTTP 网关，首版显式使用单 worker；挂载模型别名配置，由环境变量等部署配置提供上游厂商凭证。
- **postgres**：持久化平台业务数据，并为 LiteLLM 提供独立逻辑数据库。

四服务数量包含本项目自部署的 LiteLLM，不能继续将整套交付称为原先的“应用＋数据库两容器”。Nginx 属于前端服务，无需另加一个入口容器。

## 数据与网关边界

- PostgreSQL 实例内分别使用 `promptdone` 与 `litellm` 数据库，配置独立数据库用户；平台迁移与 LiteLLM 迁移各自负责本库，互不接管业务表。角色名属于 PostgreSQL 实例范围，应采用可区分的名称。
- 共用 PostgreSQL 实例是本决策的组件精简取舍，并非 LiteLLM 强制要求；仍需在实现时验证对应版本的初始化、迁移、备份与恢复。
- 为 LiteLLM 启用数据库支持，以使用网关应用凭证和持久化调用/费用记录。单纯 API 转发可无数据库，但它与虚拟密钥、持久化费用管理的能力边界不同。
- 平台使用 LiteLLM 的网关访问密钥及模型别名，通过 HTTP 发起调用。厂商密钥由 LiteLLM 管理，平台页面不承担多厂商原生接口配置。
- 运行快照保留请求模型别名、平台参数及网关返回的模型标识和调用标识（若有）。模型别名可能指向多个部署，平台不能宣称冻结了网关内部路由或厂商模型版本。
- Token 按实际 usage 留存；费用保留来源与可用性。网关费用字段缺失或因费率未匹配而返回零时，不据此断言免费，沿用已确认的“未知／已知小计”展示规则。
- 超时和重试需有统一的次数与总耗时预算，避免客户端、平台与网关多层无限重试。

## 最小运行与存储约定

- 首版保持单实例、单默认工作区；共享访问口令和服务端会话保护页面/API。平台保存的网关访问密钥在服务端加密，响应与导出不返回明文。
- 原始上传文件及需要留存的导出文件使用本地持久卷；数据版本、Prompt 版本、运行快照、执行结果和人工标注使用数据库。
- 导入按容量上限执行校验，分段处理与写入；查询分页，不要求浏览器一次加载所有记录。模型调用使用有界并发，不为每条记录一次性启动无界任务。
- 浏览器仅查询持久化状态；刷新或关闭页面不取消任务。取消操作阻止尚未开始的调用；已发出的调用按其实际可确认结果记录。
- 进程重启后识别遗留未完成任务，不静默重放可能已执行的模型请求；用户手动选择记录重跑，形成新运行。
- 首版后置平台独立 Worker、Redis 和 Token SSE。LiteLLM 单 worker 模式下 Redis 不是基本转发的必需组件；未来多 worker、多副本或特定缓存功能需重新核验依赖。

## 取舍与验证边界

前后端合并为一个交付容器可以减少组件，但会将前端更新与 API 进程发布绑定。考虑本次快速独立调整的诉求，本决策选择前后端分别交付；批量执行仍保留在 API 内，以控制首版运行组件数量。

本决策不是容量或吞吐实测结果。实现验收必须覆盖符合文件上限的 49,999 条记录导入、分页查看、限并发跑测、前端独立更新、API 重载/异常中断、已完成结果保留和新批次手动重跑。真实模型并发、响应时间与费用须在实际 LiteLLM 配置下验证。
